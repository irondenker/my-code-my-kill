# SRI 무결성 검증

SRI의 동작 원리, 운영 검증 절차, 우회 조건, 케이스별 판정을 정리한 문서입니다.

## SRI(Subresource Integrity)란?

SRI는 브라우저가 JS/CSS 파일을 내려받을 때, HTML 태그의 `integrity` 속성 값(기준 해시)과 실제로 받은 파일 내용으로 계산한 해시를 비교하는 검증 기능입니다.  
두 해시가 같으면 로드하고, 다르면 해당 JS/CSS를 차단합니다.
브라우저의 SRI 자동 검증 대상은 기본적으로 `script`(JS), `stylesheet`(CSS) 리소스입니다.

예시:

```html
<script
  src="https://cdn.example.com/lib.min.js"
  integrity="sha384-Base64EncodedHash..."
  crossorigin="anonymous">
</script>
```

설명:

- `integrity`: SRI 핵심 속성입니다. 브라우저가 내려받은 리소스의 해시를 이 값과 비교합니다. 예: `integrity="sha384-Base64EncodedHash..."`
- `crossorigin="anonymous"`: SRI 자체는 아니지만, 교차 출처 리소스에서 무결성 검증/로드를 안정적으로 수행하기 위해 함께 쓰는 CORS 관련 설정입니다. 예: `crossorigin="anonymous"`

### SRI 판단 모델

1. 기준값(정답)은 "HTML 문서 해시"가 아니라, HTML 태그에 적힌 `integrity` 속성 문자열입니다.
2. 검증대상은 `src`/`href` URL에서 브라우저가 실제로 받아온 CSS/JS 와 같은 "파일 내용 전체"입니다.
3. 이 "파일 내용 전체"에는 코드 본문뿐 아니라 공백/줄바꿈/주석까지 포함되며, **1바이트라도 달라지면 해시가 달라집니다.**
4. 브라우저는 받아온 파일로 다시 계산한 해시와 HTML 태그에 적힌 `integrity`를 비교해, 같으면 로드하고 다르면 차단합니다.
5. 따라서 SRI는 CSS/JS 등의 "리소스 파일 단독 변조"에는 강하지만, "HTML 태그 내의 `integrity`까지 같이 바뀌는 상황"에는 약해질 수 있습니다.

예시:

```html
<!-- 여기 sha384-...는 index.html 해시가 아니라 /assets/app.js 해시 -->
<script src="/assets/app.js" integrity="sha384-ABC..."></script>
```

### `integrity` 검증 절차(브라우저 동작)

1. 브라우저가 HTML 태그의 `src`/`href`에 적힌 URL에서 JS/CSS 파일을 내려받습니다.
2. 브라우저가 `integrity` 값에서 알고리즘 종류(`sha256`/`sha384`/`sha512`)와 비교할 해시 문자열을 읽어옵니다.
3. 1번에서 내려받은 JS/CSS 파일 내용 전체(공백/줄바꿈 포함)에 대해 같은 알고리즘으로 해시를 계산합니다.
4. 계산 결과(Base64 인코딩)가 `integrity` 값과 일치하면 로드/실행(또는 스타일 적용)합니다.
5. 불일치하면 리소스를 차단하고 콘솔에 SRI 오류를 남깁니다.

리소스가 차단되면 벌어지는 일:

- JS가 차단되면 해당 스크립트가 실행되지 않아 화면 기능/초기화가 일부 동작하지 않을 수 있습니다.
- CSS가 차단되면 스타일이 적용되지 않아 레이아웃이 깨지거나 기본 스타일로 표시될 수 있습니다.

SRI 오류 확인 위치(Chrome 기준):

1. `F12` -> `Console`
2. `Failed to find a valid digest in the 'integrity' attribute ...` 메시지 확인
3. `Network` 탭에서 해당 JS/CSS 요청 선택 후, 리소스는 내려받았지만 브라우저가 SRI로 차단했는지 함께 확인

    대표 오류 메시지 예:

    ```text
    Failed to find a valid digest in the 'integrity' attribute for resource 'https://...'. The resource has been blocked.
    ```

참고:

- `integrity`에는 여러 해시를 공백으로 병기(다중 해시 병기)할 수 있고, 그중 하나라도 일치하면 통과합니다.
- 파일이 1바이트라도 달라지면 해시가 바뀌므로 검증이 실패합니다.

### 다중 해시 병기

예시:

```html
<script
  src="https://cdn.example.com/app.min.js"
  integrity="sha256-AAA... sha384-BBB... sha512-CCC..."
  crossorigin="anonymous"></script>
```

#### 다중 해시 병기를 쓰는 이유

1. 알고리즘 전환기 대응(예: `sha256` -> `sha384/sha512`)을 단계적으로 진행할 때
2. 짧은 배포 전환 구간에서 브라우저/캐시 불일치로 인한 장애를 줄일 때
3. 특정 환경 호환성을 위해 임시로 복수 메타데이터를 둘 때

#### 다중 해시 병기 일치 판정 과정

1. 브라우저가 `integrity`에 적힌 해시 후보들(`sha256`, `sha384`, `sha512`)을 읽습니다.
2. 내려받은 같은 파일 내용으로 각 알고리즘 해시를 계산합니다.
3. 계산 결과 중 하나라도 `integrity`에 적힌 값과 정확히 같으면 통과합니다.
4. 하나도 일치하지 않으면 SRI 위반으로 차단합니다.

#### 보안 관점 정리(다중 해시 병기를 쓰면 보안에 불리해지나?)

전제:
아래 설명은 "같은 URL이 공백/줄바꿈 포함해 글자 하나도 바뀌지 않은 완전히 같은 파일을 가리킨다"는 배포 원칙을 기준으로 합니다.

1. "같은 파일"에 대한 복수 알고리즘 해시 병기 자체가 치명적이지는 않습니다.
2. 하지만 "서로 다른 파일 버전" 해시를 함께 넣으면 허용 범위가 넓어져, 공격자가 구버전(취약 버전)을 보내도 통과할 수 있습니다.  
   (여기서 "서로 다른 파일 버전"은 예를 들어 `app.js v1.2.0` 해시와 `app.js v1.3.0` 해시를 같은 `integrity`에 동시에 넣는 경우를 뜻합니다.)
3. 그래서 `한 릴리스 = 한 파일 해시`를 기본으로 하고, 다중 해시는 전환 기간에만 짧게 사용 후 제거하는 것입니다.

#### 올바른 예 vs 나쁜 예

| 구분 | 예시 | 왜 괜찮거나/위험한가 |
| --- | --- | --- |
| 올바른 예 | 같은 `app.js v1.3.0` 파일에 대해 `sha384`와 `sha512`를 함께 병기 | 같은 파일 하나만 허용하므로 허용 범위가 넓어지지 않음 |
| 나쁜 예 | `app.js v1.2.0` 해시와 `app.js v1.3.0` 해시를 동시에 병기 | 구버전(취약 버전)까지 유효해져 롤백/캐시 악용 시 통과 가능 |

#### 나쁜 예가 실제로 성립하기 위한 전제 조건

1. 구버전 파일 내용(옛 버전 응답 데이터)이 응답이 전달되는 경로 어딘가에 남아 있어야 합니다. (CDN/프록시/브라우저 캐시, 롤백 아티팩트 등)
2. 해당 구버전 해시가 `integrity`에 함께 남아 있어야 합니다.
두 조건이 동시에 만족될 때만 "구버전이 와도 SRI 통과"가 발생합니다.

#### 나쁜 예의 성립 조건은 까다로운데, 왜 여전히 유효한 위협으로 보는 걸까?

- "조건부 위협"인데다 성립 조건 자체도 까다롭지만, 실무에서 배포·캐시 운영 실수(캐시 미정리, 롤백 아티팩트 잔존, 해시 정리 누락)가 **실제로 자주 발생하기 때문에**  무시하기 어렵습니다.

올바른 예(같은 파일, 다른 알고리즘):

```html
<script
  src="https://cdn.example.com/app-v1.3.0.js"
  integrity="sha384-HASH_OF_V1_3_0 sha512-HASH_OF_V1_3_0"
  crossorigin="anonymous"></script>
```

나쁜 예(다른 파일 버전 동시 허용):

```html
<script
  src="https://cdn.example.com/app.js"
  integrity="sha384-HASH_OF_V1_2_0 sha384-HASH_OF_V1_3_0"
  crossorigin="anonymous"></script>
```

#### 다중 해시 병기 권장 사용 규칙

1. 해시를 여러 개 넣어도 "같은 파일" 해시만 넣습니다.
2. 파일 버전이 바뀌면 이전 버전 해시는 즉시 제거합니다.
3. 가능하면 파일명 자체를 버전/해시 기반(`app.abc123.js`)으로 고정합니다.

### SRI 운영 검증 절차

1. 빌드된 JS/CSS 파일 바이트 기준으로 해시를 생성합니다.
2. HTML 템플릿의 `integrity` 값을 같은 해시로 갱신합니다.
3. HTML과 정적 파일을 "같은 릴리스 단위"로 배포합니다(버전 불일치 방지).
4. 브라우저 콘솔/네트워크에서 SRI 오류(`Failed to find a valid digest`) 유무를 확인합니다.
5. JS/CSS 파일이 바뀌면 `integrity`도 반드시 함께 갱신합니다.

### 실행 주체와 연관 대상

1. 실행 주체:
브라우저가 SRI 검증을 수행합니다. 서버가 아니라 "클라이언트 로드 시점"에 검증됩니다.
2. 연관 대상:
주로 `<script src="...">`, `<link rel="stylesheet" href="...">` 같은 서브리소스가 대상입니다.
3. 보호 시점:
리소스를 실행/적용하기 직전에 검증하며, 실패 시 해당 리소스만 차단됩니다.

### SHA 알고리즘 선택과 판단 방식

1. `integrity`에는 `sha256`/`sha384`/`sha512`를 사용할 수 있습니다.
2. 브라우저는 선언된 메타데이터에서 더 강한 알고리즘을 우선 평가합니다(일반적으로 `sha512` > `sha384` > `sha256`).
3. 동일 강도 알고리즘 해시를 여러 개 적은 경우(공백 구분), 그중 하나와 일치하면 통과합니다.

#### SHA에 '키'는 없다

1. SRI의 SHA는 "키 없는 해시"입니다. (`HMAC`처럼 비밀키를 쓰지 않음)
2. 따라서 SRI 운영 포인트는 "키 관리"가 아니라 "파일이 바뀌면 HTML의 `integrity` 값도 같은 배포에서 함께 갱신하는 것"입니다.
3. 해시는 CI/CD에서 산출하고, HTML 템플릿의 `integrity`와 항상 같은 버전으로 배포해야 합니다.
4. 비밀키 기반 무결성/서명 검증이 필요하면 SRI가 아니라 코드서명/서명 검증 체계를 추가해야 합니다.

### SRI의 한계

1. HTML 자체가 변조되면(`src`/`integrity` 동시 변경) SRI만으로 방어할 수 없습니다.
2. 같은 오리진이 침해되어 공격자가 HTML과 정적파일을 함께 바꾸면 SRI 효과가 줄어듭니다.
3. 동적 인라인 스크립트/XSS 취약점 자체는 SRI 대상이 아니며, CSP/이스케이프가 별도로 필요합니다.
4. 교차 출처 리소스는 CORS 조건이 맞지 않으면 로드/검증이 실패할 수 있어 운영 설정 점검이 필요합니다.

### 케이스별 판정표: 어떤 파일이 바뀌면 어떻게 보이나

| 케이스 | 오리진 침해 여부 | 변경된 것 | 브라우저 판정 | 결과 | 공격자 의도 성립 |
| --- | --- | --- | --- | --- | --- |
| 정상 배포 | 없음 | 없음 | 해시 일치 | 정상 로드 | 해당 없음 |
| 리소스만 변조 | 없음(중간 경로 변조 등) | JS/CSS만 변경 | 해시 불일치 | 차단(SRI 탐지) | 실패 |
| HTML만 잘못 갱신(운영 실수) | 없음 | `integrity`만 변경 | 해시 불일치 | 차단(장애 형태) | 해당 없음 |
| HTML+리소스 동시 변경(오리진 장악) | 있음 | `integrity`와 JS/CSS 모두 변경 | 해시 일치로 통과 | 정상처럼 로드 | 성립 가능 |
| HTML에서 `integrity` 제거 | 있음 또는 배포 실수 | HTML 변경 | SRI 검증 자체 미실행 | 로드됨(정책 의존) | 성립 가능 |
| CDN 리소스 변조 + HTML 고정 | 없음 | CDN JS/CSS만 변경 | 해시 불일치 | 차단 | 실패 |
| 릴리스 불일치(캐시 꼬임) | 없음 | HTML/JS 버전 불일치 | 해시 불일치 | 차단(오탐처럼 보일 수 있음) | 해당 없음 |

해석 포인트:

1. "해시 변조로 인식"되는 경우는 `integrity` 기준값과 실제 파일 바이트가 다를 때입니다.
2. 공격자가 정상인 척 우회하려면, 보통 HTML의 `integrity`와 대상 파일을 함께 제어할 수 있어야 합니다.
3. 그래서 SRI는 강력하지만, 오리진 침해 시에는 CSP/배포무결성/접근통제와 결합이 필요합니다.

### 오리진(origin) 용어 정리

- 오리진은 `scheme + host + port` 조합입니다.
- 예: `https://example.com` 과 `https://example.com:443`은 같은 오리진으로 취급됩니다.
- 예: `https://example.com` 과 `https://cdn.example.com`은 호스트가 달라 다른 오리진입니다.
- "같은 오리진 침해"는 현재 페이지를 제공하는 오리진 서버가 wkcp 침해된 상태를 뜻합니다. 이 경우 HTML과 CSS/JS를 함께 바꿀 수 있어, SRI의 효과가 약해집니다.

#### 오리진 서버 침해 예시 상황

1. 배포 서버(SSH/CI 토큰) 탈취로 `index.html`과 `/assets/*.js`가 함께 교체된 경우
2. 웹서버 취약점(RCE/파일쓰기)으로 정적 파일 디렉터리를 직접 수정한 경우
3. 운영 스토리지(S3/CDN origin bucket) 권한 오설정으로 공격자가 파일을 덮어쓴 경우
4. 관리자 계정 탈취로 WAF/리버스프록시가 오리진 응답을 악성 파일로 치환하도록 바뀐 경우

#### 오리진이 침해되면, 왜 SRI의 검증 강도가 약해지는가(핵심)

1. SRI의 "정답 해시"는 HTML 파일 자체 해시가 아니라, 태그의 `integrity` 속성 값입니다.
2. 같은 오리진이 침해되면 공격자가 JS/CSS 파일과 HTML을 동시에 수정할 수 있습니다.
3. 공격자가 바뀐 파일 해시로 `integrity`도 함께 갱신하면 브라우저는 "해시 일치"로 판단해 통과시킵니다.
4. 즉 SRI는 "리소스 단독 변조"에는 강하지만, "기준값(HTML)까지 함께 변조"되면 단독 방어가 약해집니다.

#### 오리진이 침해 시나리오 간단한 PoC 예시

설명
`<script src="/assets/app.js">`처럼 HTML 태그가 가리키는 대상 JS/CSS 파일만 바뀌면 SRI가 차단하지만, HTML 태그내의 `integrity`까지 함께 바뀌면 브라우저는 일치로 판단해 로드합니다.

```html
<!-- 정상 배포 -->
<script src="/assets/app.js" integrity="sha384-HASH_GOOD"></script>
```

```js
// /assets/app.js (정상)
console.log("APP_OK");
```

```html
<!-- 오리진 침해 후 HTML도 같이 변경된 상태 -->
<script src="/assets/app.js" integrity="sha384-HASH_TAMPERED"></script>
```

#### 오리진 침해 시나리오에서의 SRI의 한계

1. 리소스 버전이 바뀌면 해시도 함께 업데이트해야 함(운영 관리 필요)
2. HTML 자체가 이미 변조되면(`integrity` 값까지 바뀌면) SRI만으로는 방어 불가
3. 외부 리소스 무결성 검증 도구이며, 서버 XSS/템플릿 취약점 자체를 대체하지는 않음

#### 오리진 침해 시나리오 대비 보안 설정 권장 조합

1. `nosniff`로 MIME 오해석 경로 축소
2. CSP(`unsafe-inline`/`unsafe-eval` 제거)로 실행 경로 제한
3. 외부 자산 최소화(로컬화) + 필요 시 SRI
4. 배포 아티팩트 무결성 검증(CI 단계 해시 검증)
5. 운영 탐지(CSP 리포트, 정적 파일 해시 모니터링, 프록시 로그 상관분석)
