# XSS 이론 정리

## 1. XSS의 본질

### 1.1 정의

XSS는 제어 가능한 문자열이, **JavaScript 인터프리터**로 해석될 수 있는 경우 가능하다.
공격자는 이를 악용하여 JS 문법에 맞게 코드를 위변조하는 방식으로 이루어진다.

## 2. 브라우저는 하나의 실행기가 아니다

브라우저에서 입력받는 문자열은 JS 인터프리터를 포함하여, 다양한 형태로 용도에 맞게 해석된다.
다시 말해 브라우저로 들어온 문자열은, 브라우저가 갖고있는 **인터프리터 중 하나의 맥락으로 해석**된다.

### 2.1 주요 인터프리터

1. HTML 파서 → DOM 생성
2. JS 파서 → AST 생성 → 실행
3. CSS 파서 → CSSOM 생성
4. URL 파서 → 네비게이션/리소스 로딩
5. JSON/XML 파서 → 구조 파싱

### 2.2 인터프리터 해석 경로 모델

```text
[문자열]
    ↓
어느 인터프리터로 들어가는가?
    ↓
해석
    ↓
구조 생성 / 실행 / 네비게이션
```

XSS는:

> 문자열이 JS 인터프리터로 해석되는 경우

## 3. 파서 전이 개념

### 3.1 데이터 상태 vs 해석 상태

* 문자열: 아무런 해석이 이루어지지 않은 날것의 텍스트
* 해석: 파서에 들어가 구조를 가지거나 의미를 갖는 상태

전이란:

> 문자열을 파싱하여 해석 상태로 이동하는 것

## 4. JS 인터프리터 (AST)

### 4.1 실행 과정

1. Lexing (토큰화)
2. Parsing (AST 생성)
3. Compilation
4. Execution

> `eval`, `new Function`, 문자열 타이머 등의 메서드는 **런타임에 이 과정을 다시 호출한다.**

## 5. HTML 파서와 JS 전이

### 5.1 innerHTML

```text
문자열 → HTML 파서 → DOM 생성
```

구조 생성 후:

* script 태그
* 이벤트 속성
* javascript 스킴

등을 통해 **JS 인터프리터를 다시 호출**하여 일부 코드를 HTML 재파싱할 가능성이 발생함.

### 5.2 textContent

* 문자열 → 단순 텍스트 노드
* 이미 안정화된 **텍스트 노드(DOM 객체 형태)로 생성**하여, **DOM 트리에 갖다붙임**
* HTML 파서 재진입 없음
* innerHTML에 비해 비교적 안전

## 6. 이벤트 핸들러 속성 vs addEventListener

### 6.1 이벤트 속성

```text
setAttribute("onclick", "...")
```

* 문자열 → JS로 컴파일 → 실행
* **inline script**로 간주됨.

### 6.2 addEventListener

```text
addEventListener("click", handler)
```

* 함수 객체를 전달하는 방식
* 문자열을 JS 코드로 **직접 전달하거나 파싱하는 과정이 없음**
* 비교적 현대적이고 안전한 문법

## 7. eval 계열

* `eval`
* `new Function`
* 문자열을 사용하는 `setTimeout`
* 문자열을 사용하는 `setInterval`

문자열 → **JS 파서 재진입**

CSP에서 `unsafe-eval`이 이와 관련이 있음.

## 8. URL 인터프리터

### 8.1 URL 파싱

* 문자열 → `scheme`/`host`/`path` 분해

### 8.2 javascript 스킴

```text
URL 파서 → scheme=javascript → JS 엔진 전달
(javascript://)
```

이 과정에서, URI/URL로 불러온 값이 사용자의 의사와 다르게 **JS 인터프리터로 해석될 여지**를 만들 수 있음

## 9. CSP와 실행 통제

CSP는 구조 생성을 막는 게 아니라 실행 단계에서 개입한다.
(추가 학습 필요)

## 10. XSS 유형

### 10.1 Stored

입력 → DB 저장 → 피해자 접속 시 실행

### 10.2 Reflected

요청값 → 응답에 반영 → 즉시 실행

### 10.3 DOM

클라이언트 JS 내부에서 전이 발생

### 공통점

Source는 다르지만
Sink와 실행 모델은 동일

## 11. Source–Sink 모델

### 11.1 Source

* Query
* Path
* Hash
* Header
* localStorage
* postMessage
* DB 값

### 11.2 Sink

* innerHTML
* outerHTML
* insertAdjacentHTML
* eval 계열
* setAttribute("on...")
* location/href (특정 맥락)

---

## 12. Self-XSS vs DOM XSS

### 12.1 Self-XSS

* 사용자가 직접 콘솔 실행
* 강제성 없음
* 취약점으로 인정되지 않는 경우 있음

### 12.2 DOM XSS

* 링크 클릭만으로 자동 실행
* 앱 코드 설계 취약점

핵심 차이:

> 희생자의 기술적 개입 없이 자동으로 실행이 가능한 형태인가?

## 13. XSS과 기타 Injection의 차이

| 유형         | JS 실행 | 분류             |
| ---------- | ----- | -------------- |
| CSS 변조     | ❌     | CSS Injection  |
| URL 리다이렉트  | ❌     | Open Redirect  |
| JS 실행 발생   | ✔     | XSS            |

**JS 실행이 수반되는 경우**가 XSS이다.

<참고> 위험도 판단 기준

* 기술적 기준
  * JS 실행 가능?
  * 자동 실행 가능?
  * CSP 존재?

* 맥락 기준
  * 결제/계정 변경 화면?
  * 관리자 화면?
  * 사용자 개입 필요?

> XSS가 아니더라도, **민감한 맥락에서 발생**한 취약점은 **충분히 치명적**일 수 있다!

## 14. 구상한 인터프리터 우선순위

| 인터프리터 | 위험도 |
| ----- | --- |
| JS    | 최고  |
| HTML  | 중간  |
| URL   | 중간  |
| CSS   | 낮음  |

> 자의적인 분류 기준이므로, 실제 위험도와 다를 수 있음.

## 15. 구상한 권장 점검 순서

1. Source 파악
2. Sink 탐색
3. 인터프리터 전이 확인
4. CSP 확인
5. 실행 트리거 확인
6. 영향도/위험도 분석

> 자의적인 분류 기준이므로, 실제 과정과 다를 수 있음.

## 16. 결론

> XSS는 문자열이 JS 인터프리터로 전이되어 피해자 권한으로 실행되는 현상이다.

Stored/Reflected/DOM은 전달 방식 분류일 뿐이다.

본질은:

> 인터프리터 전이 + 권한 모델

항상 이 질문을 던진다:

1. 이 값은 사용자의 입력을 받을 수 있는 문자열인가?
2. 이 문자열은 어느 종류의 인터프리터로 전이되는가?
3. 이 인터프리터가 의도적/비의도적으로 JS 인터프리터에 도달하는가?
4. 희생자의 의도와 상관없이, 기술적인 개입 없이 실행될 수 있는가?
